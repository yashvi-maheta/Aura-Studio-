## Aura Studio — Queue Business Logic Reference

**Version:** 1.0
**Last updated:** 2025
**Based on:** Actual implemented server and client code

> This document describes the behaviour as it is implemented. Items not yet implemented are clearly marked.

## 1. Customer Registration Flow

### Entry point
Customer navigates to `/join`.

### Steps

1. **Page loads:** `GET /api/services` and `GET /api/stylists` are called in parallel. The form renders with live data from the backend.

2. **Customer fills in details:**
   - Full name (required, 2–60 characters).
   - Phone number (required, 7–15 digits after stripping formatting characters).
   - Selects one active service.
   - Optionally selects a preferred stylist (default: "Any Available Stylist" = `stylistId: null`).

3. **Form submission:** `POST /api/queue/join` is called with:
   ```json
   {
     "customerName": "string",
     "phone": "string",
     "serviceId": "string",
     "stylistId": "string | null"
   }
   ```

4. **Backend processing (server/src/queue.js → joinQueue):**
   - Validates that the service exists and is active.
   - Validates that the stylist exists and is active (if one was selected).
   - Calls `nextTokenLabel()` inside a SQLite transaction to get the next sequential label (e.g. `A-01`).
   - Generates a UUID v4 as the token's internal ID.
   - Counts existing `waiting` tokens for today and sets the new token's initial position to that count + 1.
   - Inserts a row into the `tokens` table with status `waiting`.
   - Calls `recalculateQueue()` to recompute positions and EWT for all waiting tokens.
   - Returns the full token record via `getQueueSnapshot()`.

5. **Backend broadcast:** `io.emit('queue:updated', { snapshot })` is sent to all connected Socket.IO clients.

6. **Frontend confirmation:** The form is replaced by the confirmation view showing the token label, position, estimated wait, service name, and stylist name. A "Track My Position" link navigates to `/track/:tokenId`.

### Validation and errors

| Check | Where enforced | Error returned |
|-------|---------------|----------------|
| customerName present | Server | 400 `customerName is required.` |
| serviceId present | Server | 400 `serviceId is required.` |
| Service active | Server | 400 `Service not found or inactive.` |
| Stylist active (if selected) | Server | 400 `Stylist not found or inactive.` |
| Daily limit (99 tokens) | Server | 400 `Daily queue limit of 99 tokens reached.` |
| Name length | Client | Inline error; not re-validated server-side |
| Phone format | Client | Inline error; not re-validated server-side |

## 2. Queue Token Generation

### Token label format
`A-{NN}` where `NN` is zero-padded to 2 digits (e.g. `A-01`, `A-07`, `A-99`).

### Counter mechanics (server/src/queue.js → nextTokenLabel)
- Table: `daily_counters (date TEXT PRIMARY KEY, counter INTEGER)`.
- On each registration: `INSERT INTO daily_counters (date, counter) VALUES (today, 1) ON CONFLICT(date) DO UPDATE SET counter = counter + 1`.
- The counter value after increment becomes the token number.
- Wrapped in a `better-sqlite3` transaction to prevent duplicate labels under concurrent requests.
- Maximum: 99 tokens per day. Attempting a 100th registration returns a 400 error.

### Token internal ID
- UUID v4 generated by the `uuid` package.
- Used as the primary key in the `tokens` table.
- Used in the tracking URL `/track/:id`.
- Never guessable by incrementing or predicting.

### Daily reset
- A `setTimeout` chain in `server/src/index.js` fires at 00:00:01 each night (server local time).
- It runs `UPDATE tokens SET status = 'cancelled', cancelled_reason = 'day_ended' WHERE queue_date = yesterday AND status = 'waiting'`.
- After cancelling remaining tokens, it broadcasts the updated snapshot.
- The `daily_counters` table row for yesterday is not deleted; a new row is inserted for the next day, so the counter resets to 1 automatically.

## 3. Queue Position and Estimated Wait Time

### Position assignment
- On registration: position = count of `waiting` tokens today + 1.
- Recalculated after every state change (registration, call-next, transition) by `recalculateQueue()`.

### recalculateQueue (server/src/queue.js)
1. Fetches all `waiting` tokens for today, ordered by position ASC then created_at ASC.
2. Re-assigns sequential positions (1, 2, 3, …) in that order using an `UPDATE` transaction.
3. Fetches all `in_service` tokens and calculates remaining service time for each busy stylist:
   `remaining = max(0, duration_min - elapsed_minutes)`
4. Counts total active stylists and derives available slots.
5. Builds an EWT map keyed by position using the slot-simulation algorithm from docs/01-brief.md §4.3.

### EWT algorithm (implemented)
```
slots = [0 × availableStylists] + [remaining_j for each busy stylist]
slots.sort() ascending

for each customer ahead (W customers):
    earliest = index of min(slots)
    slots[earliest] += customer_i.duration_min

EWT = max(0, min(slots))
EWT_display = ceil(EWT / 5) × 5   // round up to nearest 5 minutes
```

Average service duration from active services is used as a fallback for `D_avg`.

### Position in the response
- `position`: 1-based integer; 0 for non-waiting tokens.
- `customersAhead`: `max(0, position - 1)`.
- `estimatedWaitMinutes`: from the EWT map.

## 4. Token Status State Machine

### Valid statuses (defined in client/src/components/ui/StatusBadge.tsx)
```
'waiting' | 'called' | 'in_service' | 'completed' | 'no_show' | 'cancelled'
```

### Allowed transitions (server/src/queue.js → ALLOWED_TRANSITIONS)

```
waiting    → called       (staff calls next customer)
waiting    → cancelled    (customer self-cancel via DELETE /api/queue/token/:id)
waiting    → no_show      (staff marks no show)

called     → in_service   (staff marks in service)
called     → waiting      (staff returns to queue)
called     → no_show      (staff marks no show)
called     → cancelled    (staff cancels)

in_service → completed    (staff completes service)
in_service → no_show      (staff marks no show)
```

### Terminal statuses
`completed`, `no_show`, `cancelled` — no further transitions are allowed. Attempting one returns a 400 error.

### Customer-facing labels

| Internal value | Displayed label |
|---------------|----------------|
| `waiting` | Waiting |
| `called` | Called |
| `in_service` | In Service |
| `completed` | Completed |
| `no_show` | No Show |
| `cancelled` | Cancelled |

## 5. Staff Actions

All staff actions require an authenticated staff session (cookie set by `POST /api/auth/staff/login`).

### Staff Login
- `POST /api/auth/staff/login` with `{ stylistId, pin }`.
- PIN is bcrypt-verified (cost 10 on server).
- 5 consecutive failed attempts lock the account for 10 minutes.
- On success: a signed HTTP-only session cookie is set (8-hour expiry).
- An outer express-rate-limit applies: 10 requests/minute per IP.

### Call Next (`POST /api/queue/call-next`)
- Server checks whether the calling stylist already has a `called` or `in_service` token. If so, returns a 400 error with the existing token label.
- Selects the next `waiting` token (lowest position, then oldest created_at) in a SQLite transaction.
- Sets its status to `called` and assigns `assigned_stylist_id` to the calling stylist.
- Calls `recalculateQueue` and broadcasts `queue:updated`.
- **Race condition protection:** the `UPDATE … WHERE id = ? AND status = 'waiting'` transaction means two simultaneous "Call Next" requests will not assign the same customer to two stylists.

### Mark In Service (`PUT /api/queue/token/:id/status`, body `{ status: 'in_service' }`)
- Validates the transition: `called → in_service` only.
- Updates the token; `updated_at` is used as the service-start time for EWT calculations.
- Recalculates and broadcasts.

### Complete Service (`PUT /api/queue/token/:id/status`, body `{ status: 'completed' }`)
- Validates: `in_service → completed` only.
- Removes the stylist from the active queue; counted in revenue statistics.

### No Show (`PUT /api/queue/token/:id/status`, body `{ status: 'no_show' }`)
- Valid from `waiting`, `called`, `in_service`.
- Token is not counted in revenue.

### Return to Waiting (`PUT /api/queue/token/:id/status`, body `{ status: 'waiting' }`)
- Valid from `called` only.
- Position is recalculated; the customer re-enters the queue.

## 6. Customer Cancellation

### Self-cancel
- `DELETE /api/queue/token/:id` (unauthenticated).
- Backend calls `transitionToken(id, 'cancelled', 'Customer cancelled')`.
- Valid only while status is `waiting` (enforced by `ALLOWED_TRANSITIONS`).
- **Note:** A "Cancel my token" button is not currently present in the customer tracking UI. The backend endpoint exists and is functional, but it is not wired to any front-end action on the tracking page. This is a known gap.

## 7. Real-Time Updates

### Server → all clients: `queue:updated`
Emitted after every queue state change (registration, call-next, any status transition, midnight reset).

Payload:
```json
{
  "snapshot": [ /* full array of ApiToken for today */ ]
}
```

All connected clients (TrackPage, StaffPage, DisplayPage, AdminPage) subscribe to `queue:updated` and replace their local token state with the new snapshot.

### Customer tracking room
- When `/track/:id` loads, the client emits `socket.emit('track:join', tokenId)`.
- The server joins that socket to the room `token:{tokenId}`.
- Currently unused for targeted per-token events (all broadcasts use the global `queue:updated` event). Reserved for future targeted notifications.
- On unmount: `socket.emit('track:leave', tokenId)`.

### Socket.IO connection
- Client: `socket.io-client` singleton in `client/src/lib/socket.ts`.
- Server: `socket.io` v4 attached to the Express HTTP server.
- CORS: configured to allow `CLIENT_ORIGIN` with `credentials: true`.
- In development: Vite proxy forwards `/socket.io` to `localhost:4000`.
- In production: `VITE_API_URL` must point to the backend origin; Socket.IO connects to that URL.

## 8. Validation and Error Handling

### Client-side validation (JoinPage)
- Name: required, 2–60 chars.
- Phone: required, 7–15 digits.
- Service: selection required.
- Errors shown inline; re-validated on change once shown.
- Empty-state prevention: "Join Queue" button disabled if `waiting === 0` on staff page.

### Server-side validation
- All POST/PUT endpoints check required fields.
- Status transitions are enforced by `ALLOWED_TRANSITIONS` before any DB write.
- SQL queries use parameterised statements throughout.
- Expected errors return JSON `{ error: "message" }` with an appropriate 4xx status code.
- Unexpected errors are caught and return 500 without exposing stack traces.

### Authentication errors
- `requireStaff` and `requireAdmin` middleware return `401 { error: "... authentication required." }` for unauthenticated requests.

## 9. Edge Cases

| Scenario | Handling |
|----------|---------|
| Two stylists tap "Call Next" simultaneously | SQLite transaction with `WHERE status = 'waiting'` prevents double-assignment. One request succeeds; the other receives "No customers are currently waiting." |
| Customer refreshes tracking page | `GET /api/queue/token/:id` re-fetches the current state; no localStorage dependency. |
| Backend restarts | SQLite data persists (if persistent disk is configured). Socket.IO clients reconnect automatically via `autoConnect: true`. |
| Service deleted after customer registered | The `tokens` table stores `service_id` as a foreign key; the join in `getQueueSnapshot` will still return the service name from the `services` table as long as the row exists. Services can only be disabled, not deleted. |
| Token counter reaches 99 | `nextTokenLabel()` throws; server returns 400 "Daily queue limit of 99 tokens reached." |
| Staff logs in from two tabs simultaneously | Each tab has a separate session socket. Both receive `queue:updated` events. Actions from either tab work correctly. |
| No stylists active | "Call Next" at the top of the staff page is disabled when `waiting === 0`. If no stylists are active, the queue can still receive registrations but no one can call them. |
| Admin stats endpoint returns 401 | AdminPage falls back to showing the login form (session expired or not set). |

- Admin session detection uses a staff-auth endpoint (`/api/queue/stats`) rather than a dedicated admin-me endpoint; a staff session without an admin session may cause a brief redirect to login.
